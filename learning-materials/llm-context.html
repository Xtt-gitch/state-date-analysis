CONCEPT LEARNING MATERIAL

大模型的上下文（Context / 上下文窗口）

模型每次生成时"能看到并参考"的全部内容 = 上下文；上下文窗口 = 它的容量上限（以 token 计量）。窗口之外，对模型而言"不存在"。

学科：人工智能 / 大语言模型（LLM） 难度：入门 → 进阶 别名：Context / Context Window / 上下文长度 / Token Window 检索核实：2026-09-08

1个人解释

给"上一课的自己"讲：大模型不像人那样有"长期记忆"。它每次开口前，只看得见放在它面前的一摞便签——这摞便签就是上下文：里面有系统指令、你之前说的话、它自己刚写的内容、贴进来的文档片段。便签的总容量就是上下文窗口，每张便签上写的最小文字碎片叫 token（词元）。

最常用的比喻是"固定大小的黑板 / 草稿纸 / 工作台"：你问的问题、模型的回答、历史聊天都写在同块黑板上；写满之后，为了写新内容，最早写上去的字会被擦掉——这就是为什么聊久了、喂长了，模型会"忘记"最开始的内容：不是它变笨，是那些内容被挤出窗口了。

本质：上下文不是"记忆仓库"，而是模型一次推理（一次前向计算）能处理的最大 token 序列。应用层可以偷偷帮你把旧对话摘要存档、存进数据库——但只要没放进这次请求的上下文里，模型就看不到。

一句话直觉：窗口大 = 桌子大 = 能同时摊开的资料多；但桌子再大，人（模型）也只会重点看摆在开头和结尾的材料（见 4.2）。"能不能放得下"和"会不会用得好"是两回事。

2核心机制

2.1 从文本到 token

模型不读"字"，读的是分词器（tokenizer）切出来的 token 编号序列。一个 token 可能是整词、子词或符号。不同来源给出的换算口径略有差异（与分词器有关）：常见说法是英文约 3–4 个字符 ≈ 1 token（约 0.75 词）；中文大致 1 个汉字 ≈ 1 token（也有资料称 1.5–2 汉字 ≈ 1 token）。差异即事实：token 数必须用具体模型的分词器实测，不能按字数拍脑袋。

2.2 为什么窗口是"硬"上限：自注意力

Transformer 的核心是自注意力：序列里每个 token 都要与其他所有 token 计算关联。若序列有 N 个 token，注意力计算量约为 N×N——呈平方级增长（长度翻倍，计算与 KV 缓存显存约变 4 倍）。这就是上下文窗口存在且被限制的架构原因：窗口上限 = 允许参与自注意力的最大 token 数。因此还有一条推论：输入若超过窗口，超出部分会被截断，且完全不参与计算——模型对它"一无所知"。

        ▼
2 分词：文本 → token 序列 → 向量化（embedding）+ 位置编码（模型本身不"认识"顺序）

4 逐 token 生成：预测下一个 token → 新 token 追加进序列，成为预测再下一个的上下文

5 输出同样占窗口：输入占了 90%，就只剩 10% 空间给回答；满了即触顶截断

2.4 窗口满了怎么办：四种常用策略

  • 截断（Truncation）：直接丢掉最旧内容——简单粗暴，但可能丢掉早期指令。
  • 滑窗（Sliding Window）：只保留最近 N 个 token。
  • 摘要压缩（Summarization）：把旧轮次压成摘要再放回窗口，省空间但丢细节。
  • 检索增强（RAG）：长文档切片入库，按相关性只取 Top-K 片段进窗口——外部库无限大，窗口只放"最该看的"。这也是 RAG 存在的重要原因之一。

2.5 关键现象：Lost in the Middle（中间迷失）

斯坦福等机构的论文（Liu et al., 2023）发现：把"含答案的文档"放在上下文不同位置测试，模型性能呈 U 形曲线——放在开头或结尾时找得准，放在中间时准确率明显下滑，即便对号称长上下文的模型也如此。也就是说"能看到"不等于"会用到"。

模型取用上下文信息的可靠性（示意，U 形）

    │  ●                                  ●
    │    ●                            ●
    │      ●                      ●
 低 │        ● ──────────── ●

工程含义：最重要的指令放最前、当前任务放最后、关键材料放开头或结尾；中间区域默认"可能被忽略"。另外，更长的输入还意味着更高的延迟、显存与费用，且可能引入干扰信息——"塞满窗口"通常是下策。

2.6 演进中的窗口规模（时点快照）

按 2024 年前后资料：GPT-3.5 约 4K → GPT-4o / Llama 3.1 / Mistral Large 2 等支持 128K → Claude 3.5 Sonnet 200K → Gemini 1.5 Pro 最高约 2M token（百度百科与多篇技术资料可互证）。到 2026 年主流模型窗口普遍已达数百 K 至 1M 量级。注意：具体规格随版本快速变化、且"理论窗口"与"接口允许的最大输入/输出"常不一致——数字请以各厂商官方文档为准，本段仅示意演进趋势。

3应用场景

3.1 长文档分析（一次性读入"书级"输入）

何时用：合同、论文、年报等几十上百页文档要整体理解。为什么：窗口大到能装下全文，省去切片的麻烦。怎么用：把全文（必要时先转文本）放进窗口再提问。但要用对位置：关键段落若埋在中间可能被忽略；内容极长时仍建议 RAG/分段处理，而非无限塞。

3.2 RAG：给有限窗口配一个"无限资料库"

何时用：知识库问答、企业文档答疑——资料总量远超任何窗口。为什么：向量检索能把"最相关的几段"选出来，让窗口预算花在刀刃上。怎么用：文档切片→向量化入库→按问题召回 Top-K→与问题一起进窗口生成。经验：Top-K 不必贪大（10–20 已常见），宁用精排少而准，关键片段尽量放开头或结尾。

3.3 Agent 长任务与多轮对话中的上下文管理

何时用：Agent 反复调用工具、多轮对话持续累积，或聊天历史超长。为什么：每轮工具结果、对话都回流窗口，越滚越长——成本（按 token 计费，输入通常是成本大头）与效果双恶化。怎么用：层级化管理：系统指令常驻并开启缓存；会话摘要动态压缩；文档与工具输出按需检索、超限裁剪。这也是很多 Agent 框架配"外部记忆/向量库"的原因：窗口负责"当下"，外部存储负责"长久"。

成本视角：API 按 token 计费，上下文越长每次请求越贵；把大量无关历史反复重发，费用会成倍上升——"主动管理上下文"首先是一笔经济账。

4边界辨析

4.1 相近概念对比

4.2 适用边界与失效条件

  • 窗口大 ≠ 用得好：Lost in the Middle 证明信息位置比信息总量更影响结果；输入过长甚至可能降低准确率。
  • "能装下" ≠ "记住了"：对话产品把旧消息"丢出窗口"，模型立即遗忘——它没有训练记忆，每次只按当前窗口重算。
  • 生成占预算：输入塞满窗口会挤压回答空间；输入上限与输出上限通常是两个独立限制。
  • 成本与性能：长输入带来更高费用、更长首字延迟（TTFT）与更大 KV 缓存显存占用，需要硬件与预算兜底。

4.3 常见误区

  1. 误区：模型"记得"我早先说过的话。纠正：它只是每次被应用把历史重新拼进上下文。一旦历史被挤出窗口或产品层决定不重发，它一无所知。
  2. 误区：把全部资料一次性塞进窗口效果最好。纠正：中间内容易被忽略、无关内容会干扰注意力，成本还高。精准放入必要信息通常优于堆量。
  3. 误区：窗口 128K 就能输出 128K。纠正：窗口是"输入+输出"总预算（且不少产品另有独立输出上限），先看具体模型的接口限制。
  4. 误区：token 换算有统一标准。纠正：不同分词器、不同语言差别很大；中文场景 token 消耗通常明显高于同义英文，务必实测估算。

诚实边界：文中窗口规格（4K/128K/200K/2M 等）为 2024 年前后多来源互证的时点快照，2026 年新模型普遍更大、且各家数值变化快；token/汉字换算在不同来源中口径不一。任何具体数字以列出来源与厂商官方文档为准。
